# ADR-009：渐进式质量门禁

## 状态
Accepted（Sprint 0）

## 背景

项目有27个Maven模块、约107个TODO方法。如果一上来就跑全量`mvn verify`，38个测试会红，CI永远过不了。但如果完全不设门禁，代码质量会失控。

## 决策

采用渐进式质量门禁，每个Sprint扩大CI范围：

| Sprint | CI运行范围 | 覆盖率门禁 | 端到端测试 |
|--------|-----------|-----------|-----------|
| S0 | co-shared-kernel + co-identity 全量测试 | 不设 | 关闭 |
| S1 | 上述 + co-qa domain/application | co-qa-domain ≥ 0.70 | 关闭 |
| S2 | 上述 + co-reputation domain/application | co-reputation-domain ≥ 0.70 | 关闭 |
| S3 | 全部模块 + CampusOverflowFlowIT | 全部领域 ≥ 0.70 | 开启 |
| S4 | 全量 `mvn verify` | 全模块 | 开启 |

## 行走骨架（Walking Skeleton）

Sprint 1开始时，Reputation/Discovery的所有@EventListener方法暂时改为空实现（只打DEBUG日志），并为其建立tech-debt Issue。到对应Sprint再实现。

空实现期间事件被标记为"已投递"。进入实现Sprint后若需重放：
```sql
UPDATE outbox_event SET published_at = NULL, attempts = 0;
```

## 理由

1. 每个Sprint结束时CI都是绿的，软件可运行、可演示
2. 避免"等全部写完再联调"的后期地狱
3. 覆盖率门禁只卡领域层，不卡应用层和接口层，避免过度测试

## 后果

- Sprint 1-2的CI时间较短（只跑部分模块）
- 需要在Sprint 3移除所有行走骨架空实现
- 团队需自觉维护tech-debt Issue不被遗忘
