# CampusOverflow Team3 · 跨成员 PR 评审清单 v1.0

> 用途：Lab7（#33）跨成员 PR 深度评审的标准检查表。评审人按本清单逐项检查，每个 PR 至少留下 5 条实质性意见。
> 维护：SM（肖蕴晨）牵头，团队评审时共同修订。
> 适用范围：所有合并进 `develop` 的 PR，代码类必查，文档类可跳过不适用的条目。

## 0. 合并前置（硬性，不满足不合并）

- [ ] PR 目标分支是 `develop`（不是 main）
- [ ] 标题符合规范：`类型(模块): 简述（Closes #issue号）`
- [ ] 没有直接 push `main` / `develop`（必须走 PR）
- [ ] 没有修改或删除仓库已有测试断言（红测试是需求说明书，只能补实现）
- [ ] PR 描述含自检清单与验证方式（本地跑的什么命令、结果如何）
- [ ] 至少 1 名非作者 Approve

## 1. 正确性（最优先）

- [ ] 逻辑是否符合 issue 的验收标准，逐条对应
- [ ] 边界条件是否覆盖：空值、超长输入、非法状态、并发重复操作
- [ ] 状态流转是否完整（如 Question：已删除/已采纳/已关闭后不能继续操作）
- [ ] 异常路径是否有明确错误类型与状态码（403/409/422 等），语义是否准确
- [ ] 领域不变量是否在领域层校验，而不是散落在应用层/接口层

## 2. 可读性

- [ ] 命名是否表达意图（方法名=动作+对象，变量名不用缩写歧义）
- [ ] 方法长度是否合理（建议 ≤ 40 行，过长应拆小方法）
- [ ] 注释是否解释"为什么"，而不是复述"做了什么"
- [ ] 复杂逻辑是否有必要的中文注释（团队以中文沟通为主）
- [ ] TODO/FIXME 是否有 issue 号或说明

## 3. 可测性

- [ ] 是否容易为该方法写单元测试（依赖是否可注入）
- [ ] 是否有隐藏副作用（静态状态、全局单例、直接 IO）
- [ ] 时间是否注入（`Instant now` 参数），避免测试依赖真实时钟
- [ ] 纯逻辑是否与 IO 分离（领域层不直接依赖数据库/HTTP）

## 4. 安全

- [ ] 权限校验：非作者/非管理者操作是否被拒绝（403）
- [ ] SQL 注入：是否使用参数绑定，杜绝字符串拼接 SQL
- [ ] XSS：前端渲染用户内容是否转义；后端是否对输入做长度/格式校验
- [ ] 越权：水平越权（改别人的资源）、垂直越权（低权限干高权限的事）
- [ ] 敏感信息：日志里不打印密码、token、个人信息

## 5. 性能

- [ ] 是否存在 N+1 查询（循环内查库）
- [ ] 缓存使用是否合理（读多写少、一致性要求低才适合缓存）
- [ ] 批量场景是否循环单条提交
- [ ] 数据库索引与查询是否匹配（当前阶段只做静态判断）

## 6. 风格与规范

- [ ] 符合后端（Spring Boot 3 / Java 21）或前端（React 18 / TS）既有代码风格
- [ ] 模块内依赖方向正确（domain 不依赖 application/infrastructure）
- [ ] 提交信息清楚：做了什么 + 怎么验证（不写 "update"）
- [ ] 无关文件是否混入（如 IDE 配置、临时文件）

## 7. 评审记录要求

- [ ] 每条意见写清楚：文件/方法 + 问题 + 建议改法（或疑问点）
- [ ] 实质性意见 ≥ 5 条（"LGTM" 不算）
- [ ] 区分"必须改"（合并阻塞）与"建议"（可后续优化）
- [ ] 评审结束后在群里同步一句结论

## 附：评审流程（参考执行说明 7 步）

1. 认领：在 issue 右侧 Assignees 选自己，或群里声明
2. 从最新 `develop` 切分支，命名 `docs/33-review-checklist` 同类风格
3. 按 issue"具体步骤"干活，先本地验证
4. 按验收标准逐条自检
5. 提 PR：目标 `develop`，标题带 `Closes #issue号`
6. 至少 1 人 Approve 后 SM 合并
7. 合并后 issue 自动关闭，群里同步
