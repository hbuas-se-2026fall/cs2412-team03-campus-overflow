## 二、Retrospective（回顾）

### Keep（继续保持）

1. **先批准、再轮询、后合并**：`blocked` 多为缺批准而非落后，先发 Approve 再等 `mergeable_state` 转 clean。
2. **Issue 闭环以主干代码为准**：#10、#12 是核对 `Question.java` / `Vote.java` / `Comment.java` 与对应测试后才关的，没有凭 Issue 状态下结论。
3. **PR 正文写清"做了什么 / 证据 / 未验收项"**：deadlie 的 PR 都带了文件级说明和待验证项，评审成本明显更低。

### Drop（不再继续）

1. **PR 正文写 `Closes #x` 却不核对是否真关**：#10、#12 因此一直挂在 open，造成"看起来没做"的假象。
2. **合并脚本在 PUT 失败时仍关 Issue**：#37–#40 曾因此误关一次，虽已回退，但脚本必须只以 `PUT` 返回 200+sha 作为关闭条件。
3. **把团队自加严的 DoD 当成课程硬门槛**：Docker 真机验证是内部加严项，不是老师明文指标，不应卡住主干推进。

### Start（开始做）

1. **串行合并**：一次只合一个 PR，合完立刻通知其余作者 Update branch，避免连环 behind。
2. **未验收项一律另开 Issue 追踪**，不在 PR 里写成"已完成"。
3. **每次合并后回读一次快照**：HEAD + Issue 状态，防止状态漂移。
