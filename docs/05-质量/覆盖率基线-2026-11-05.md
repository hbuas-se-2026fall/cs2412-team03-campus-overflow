## 1. 复现方式

环境：Windows / JDK 21.0.12.1 / Apache Maven 3.9.16 / **无 Docker**。
基线 commit：`d4843fa`（develop，含已合并的 #69、#71）。

```bash
# 常规跑法：会在 co-qa-application 处失败（见第 3 节红测试清单）
mvn -B -f backend/pom.xml test jacoco:report

# 取全量覆盖率时允许测试失败继续，才能生成所有模块的报告
mvn -B -f backend/pom.xml test jacoco:report -Dmaven.test.failure.ignore=true

# HTML 报告（Issue #31 的输出物，target/ 不入库）
# 各模块：backend/<module>/target/site/jacoco/index.html
```

口径说明：下表只统计**实际生成了 `jacoco.xml` 的 7 个模块**，`LINE` 计数器。`*-api`、`*-infrastructure`、`*-interfaces`、`*-application`（除 co-qa-application）等模块本轮没有测试执行、未生成报告，因此**没有计入分母**；按全后端口径的真实整体覆盖率只会更低，不会更高。

### 补测内容（`DomainInvariantTest.java`）

新增 15 个用例，共 33 个领域层测试全部通过。覆盖的是真实故障面，不是为凑行数的假断言：

- `reconstitute` 全字段往返（Question / Answer / Vote / Comment）——字段错位会导致仓储写回串列；
- `assignId` 重复分配、未持久化聚合不能被采纳 / 回答；
- 已被采纳的问题不可编辑、陌生人不可删除、已删除聚合拒绝后续变更；
- `MarkdownBody` 双下限、`TagName` 空值、`Tags` 清洗后为空 / 去重后仍超限；
- `Vote` 非法值与改票返回旧值、`Comment` 一层回复、`Answer.edit` 成功路径。

按章程没有删测试、没有放宽断言、没有调低阈值。

## 3. 红测试清单与根因（重要）

全量 `mvn test` 目前**不是绿的**，CI 没暴露是因为 `.github/workflows/ci.yml` 阶段 4 用了 `continue-on-error: true`，且 `-Dsurefire.skip=true` 是无效参数（surefire 只认 `-DskipTests` / `-Dmaven.test.failure.ignore`），该步骤实际在跑全部单测再吞掉失败。

| 测试 | 结果 | 根因 |
| --- | --- | --- |
| `QuestionTest$Posting.requiresOneToFiveTags` | 本 PR 前 FAILURE | `Tags.of()` 用 `.limit(5)` 静默截断第 6 个标签，未按规格抛异常 → **本 PR 已修实现** |
| `QuestionCommandServiceTest.strangerCannotEdit` | 本 PR 前 FAILURE | 测试正文只有 17 字，低于 `MarkdownBody` 的 20 字下限，在值对象构造阶段就抛 `BusinessRuleException`，根本走不到权限校验 → **本 PR 修测试数据，断言保持 `ForbiddenException` 不变** |
| `AnswerAndVoteServiceTest`（2 个） | 仍红 | `VoteService.cast` / `resolve` 仍是 `TODO(S2)` 骨架，属 #12 / #15；PR #72 正在实现，合并后应转绿 |
| `BountyAndAccountTest` / `ReputationRulebookTest`（14 个） | 仍红 | Reputation 上下文骨架未完成，属团队其他成员的实现范围 |
| `DiscoveryDomainTest`（5 个） | 仍红 | Discovery 上下文骨架未完成 |

按团队章程「测试不删不放宽：红测试是规格说明」，本 PR **没有删除任何测试、没有放宽任何断言、没有调低任何阈值**。两处修改一处是实现补齐规格，一处是修掉会让断言变成假绿的非法输入。

## 4. 一个已知的门禁失效风险（沿用 #19 的结论）

`jacoco:check` 在找不到 `jacoco.exec` 时会静默跳过并打印 `All coverage checks have been met.`。也就是说，一旦 Q&A 单测被从 CI 移除，覆盖率门禁不会报错，只会悄悄失效。要防这个，得额外断言「测试确实执行过」（例如校验 surefire 报告数量），当前未做。

另外，#19 要求的 ci.yml 三处接线（阶段 2 模块列表加入 Q&A、新增阶段 2b 跑 `mvn verify -pl co-qa/co-qa-domain -am`、阶段 4 改 `-Djacoco.skip=true`）**仍未落地**：当前 GitHub token 只有 `repo`/`gist`/`read:org`，缺 `workflow` scope，GitHub 拒绝 OAuth App 推送任何 `.github/workflows/*.yml` 改动。补授权命令 `gh auth refresh -s workflow`，或由有权限账号在网页按 #19 评论里的三处补丁手工编辑。

## 5. 结论

- #19 的**覆盖率门槛与有效性验证**：已由 PR #72 + 本文数据覆盖，只差 CI 接线。
- #31 的**核心聚合 ≥90%**：**已达成**（`co-qa-domain` 100%，230/230，33 个测试全绿）。
- #31 的**整体 ≥70%**：**仍未达成**（42.8%）。缺口构成很明确，不是靠多写几个单测能填的：
  - `co-bootstrap` 257 行 0%：SecurityConfig / OutboxRelay / DemoDataSeeder / GlobalExceptionHandler 等启动装配层，正确覆盖方式是集成测试（`CampusOverflowFlowIT`，需 Docker）而不是一堆 mock 单测；
  - `co-reputation-domain` 9.4%、`co-discovery-domain` 26.2%：上下文骨架仍是 TODO，红测试本身跑不完，需对应实现合入；
  - `co-qa-application` 41.1%：`VoteService` TODO，PR #72 正在实现。
  - 按全后端口径（把没生成报告的模块也计入分母）只会更低。
  - 本次覆盖率是在 `-Dmaven.test.failure.ignore=true` 下取的，含失败测试模块，**不能用于宣告整体达标**。

**结论：不造假、不靠改统计口径凑 70%。** 整体覆盖率要达标，前置条件是 CI runner 上跑通集成测试 + 三个上下文骨架合入，这两项都不是单人单轮能诚实完成的。
- #34 的 `CampusOverflowFlowIT`（MySQL 8 + Redis 7 Testcontainers 全链路）代码已在 develop 上，但**本机无 Docker 未实跑**，CI 中该阶段仍 `continue-on-error`，不能算验收通过。
