## 4. 门禁失效风险与 #19 接线状态（已收口）

`jacoco:check` 在找不到 `jacoco.exec` 时会静默跳过并打印 `All coverage checks have been met.`。也就是说，一旦 Q&A 单测被从 CI 移除，覆盖率门禁不会报错，只会悄悄失效。

**这个风险已修复**：PR #75 在阶段 2b 末尾加了 `test -s backend/co-qa/co-qa-domain/target/jacoco.exec`，exec 缺失或为空就直接 `exit 1`，不再静默放过。

**#19 的三处 CI 接线也已全部落地**（PR #75）：

| 接线项 | 状态 |
| --- | --- |
| 阶段 2 模块列表加入 `co-qa/co-qa-domain` | ✅ 已落地 |
| 新增阶段 2b：`mvn verify -pl co-qa/co-qa-domain -am -Ddomain.coverage.minimum=0.70`，不加 `continue-on-error` | ✅ 已落地，另加 `jacoco.exec` 存在性断言 |
| 阶段 4 把无效的 `-Dsurefire.skip=true` 改为 `-Djacoco.skip=true` | ✅ 已落地，`continue-on-error` 保留并如实标注 |

初版曾因 GitHub token 缺 `workflow` scope 无法推送 `.github/workflows/*.yml`，后经 `gh auth refresh -h github.com -s workflow` 完成 device flow 授权，scopes 变为 `'gist', 'read:org', 'repo', 'workflow'`，工作流文件得以正式提交。这段限制已解除，不再是未决事项。

另外，PR #72 把 `qa.domain.coverage.minimum=0.70` 写进 `co-qa-domain/pom.xml`，因此**不依赖 CI 传参也能守住 0.70**；本机以「不加任何 `-D`」的方式验证过 `mvn verify -pl co-qa/co-qa-domain -am` 能加载 `jacoco.exec` 并通过门禁。

## 5. 结论

- #19 的**覆盖率门槛与有效性验证**：**已完成**（门槛数据见本文，CI 接线与 exec 断言见 PR #75，模块自带阈值见 PR #72）。
- #31 的**核心聚合 ≥90%**：**已达成**（`co-qa-domain` 100%，230/230，33 个测试全绿）。
- #31 的**整体 ≥70%**：**仍未达成**。基线为 42.8%（465/1086），PR #72 分支最新实测 55.6%（695/1249），两次都未达标。缺口构成很明确，不是靠多写几个单测能填的：
  - `co-bootstrap` 257 行 0%：SecurityConfig / OutboxRelay / DemoDataSeeder / GlobalExceptionHandler 等启动装配层，正确覆盖方式是集成测试（`CampusOverflowFlowIT`，需 Docker）而不是一堆 mock 单测；
  - `co-qa-application` 53.5%：命令服务仍有未覆盖的分支与装配路径；
  - 按全后端口径（把没生成报告的模块也计入分母）只会更低。
  - 基线那次覆盖率是在 `-Dmaven.test.failure.ignore=true` 下取的，含失败测试模块；第 6 节那次是**全绿**状态下取的，口径更干净，但同样**不能用于宣告整体达标**。

**结论：不造假、不靠改统计口径凑 70%。** 整体覆盖率要达标，前置条件仍是 CI runner 上跑通集成测试（#34）与剩余装配层补测，这不是单人单轮能诚实完成的。
- #34 的 `CampusOverflowFlowIT`（MySQL 8 + Redis 7 Testcontainers 全链路）代码已在 develop 上，但**本机无 Docker 未实跑**，CI 中该阶段仍 `continue-on-error`，不能算验收通过。

### 7.5 补测时发现的契约缺陷（已上报，本轮未改生产代码）

`QuestionQueryService.detail(...)` 构造 `PermissionsView` 时，第 4 个参数传的是 `actorOrNull != null`（源码注释写 `// canVote`），但字段名是 `canManage`；`frontend/src/pages/QuestionDetailPage.tsx:29` 正是用 `q.permissions.canManage` 控制「教师认证」按钮。**结果是任何已登录用户都会看到教师认证入口，点下去才被 `AnswerCommandService` 的 `identity.canManageCourse(...)` 拦成 403**——后端权限没漏，是前后端权限投影语义错位，`IdentityApi.canManageCourse` 在查询服务里从未被调用。

三种修法需要 PO 先确认语义：①查询服务改为调用 `identity.canManageCourse`；②字段改名 `canVote` 并同步前端；③前端另取管理权限。本轮是覆盖率补测 PR，不夹带生产行为变更。新增测试**没有断言 `canManage` 的当前值**，避免把这个疑似错误行为固化成规格。
