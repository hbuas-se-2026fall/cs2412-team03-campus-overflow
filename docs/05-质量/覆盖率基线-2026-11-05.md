## 1. 复现方式

环境：Windows / JDK 21.0.12.1 / Apache Maven 3.9.16 / **无 Docker**。
基线 commit：`d4843fa`（develop，含已合并的 #69、#71）。

```bash
# 常规跑法：在该 commit 上会在 co-qa-application 处失败（见第 3 节红测试清单）
mvn -B -f backend/pom.xml test jacoco:report

# 取全量覆盖率时允许测试失败继续，才能生成所有模块的报告
mvn -B -f backend/pom.xml test jacoco:report -Dmaven.test.failure.ignore=true

# HTML 报告（Issue #31 的输出物，target/ 不入库）
# 各模块：backend/<module>/target/site/jacoco/index.html
```

口径说明：下表只统计**实际生成了 `jacoco.xml` 的 7 个模块**，`LINE` 计数器。`*-api`、`*-infrastructure`、`*-interfaces`、`*-application`（除 co-qa-application）等模块本轮没有测试执行、未生成报告，因此**没有计入分母**；按全后端口径的真实整体覆盖率只会更低，不会更高。第 6 节沿用完全相同的口径，保证可比。

## 3. 红测试清单与根因（develop @ `d4843fa` 快照）

> 下表是基线 commit 的**历史状态**，不是当前状态。PR #72 已补齐骨架实现，并在同步 develop 时修掉了前两处红测试，目前 `feature/15-19-vote-comment-ci` 分支全量单测 **68 个全绿**（见第 6 节）。

在该 commit 上，全量 `mvn test` **不是绿的**，CI 没暴露是因为 `.github/workflows/ci.yml` 阶段 4 用了 `continue-on-error: true`，且 `-Dsurefire.skip=true` 是无效参数（surefire 只认 `-DskipTests` / `-Dmaven.test.failure.ignore`），该步骤实际在跑全部单测再吞掉失败。

| 测试 | 结果 | 根因 |
| --- | --- | --- |
| `QuestionTest$Posting.requiresOneToFiveTags` | 本 PR 前 FAILURE | `Tags.of()` 用 `.limit(5)` 静默截断第 6 个标签，未按规格抛异常 → **本 PR 已修实现** |
| `QuestionCommandServiceTest.strangerCannotEdit` | 本 PR 前 FAILURE | 测试正文只有 17 字，低于 `MarkdownBody` 的 20 字下限，在值对象构造阶段就抛 `BusinessRuleException`，根本走不到权限校验 → **本 PR 修测试数据，断言保持 `ForbiddenException` 不变** |
| `AnswerAndVoteServiceTest`（2 个） | 基线仍红 | `VoteService.cast` / `resolve` 仍是 `TODO(S2)` 骨架，属 #12 / #15；**PR #72 已实现并转绿** |
| `BountyAndAccountTest` / `ReputationRulebookTest`（14 个） | 基线仍红 | Reputation 上下文骨架未完成；**PR #72 已补齐并转绿** |
| `DiscoveryDomainTest`（5 个） | 基线仍红 | Discovery 上下文骨架未完成；**PR #72 已补齐并转绿** |

按团队章程「测试不删不放宽：红测试是规格说明」，本 PR **没有删除任何测试、没有放宽任何断言、没有调低任何阈值**。两处修改一处是实现补齐规格，一处是修掉会让断言变成假绿的非法输入。同源修复也已同步进 PR #72，使 develop 在 #72 合入后即为全绿，不依赖合并顺序。

## 4. 门禁失效风险与 #19 接线状态（已收口）

`jacoco:check` 在找不到 `jacoco.exec` 时会静默跳过并打印 `All coverage checks have been met.`。也就是说，一旦 Q&A 单测被从 CI 移除，覆盖率门禁不会报错，只会悄悄失效。

**这个风险已修复**：PR #75 在阶段 2b 末尾加了 `test -s backend/co-qa/co-qa-domain/target/jacoco.exec`，exec 缺失或为空就直接 `exit 1`，不再静默放过。

**#19 的三处 CI 接线也已全部落地**（PR #75）：

| 接线项 | 状态 |
| --- | --- |
| 阶段 2 模块列表加入 `co-qa/co-qa-domain` | ✅ 已落地 |
| 新增阶段 2b：`mvn verify -pl co-qa/co-qa-domain -am -Ddomain.coverage.minimum=0.70`，不加 `continue-on-error` | ✅ 已落地，另加 `jacoco.exec` 存在性断言 |
| 阶段 4 把无效的 `-Dsurefire.skip=true` 改为 `-Djacoco.skip=true` | ✅ 已落地，`continue-on-error` 保留并如实标注 |

初版曾因 GitHub token 缺 `workflow` scope 无法推送 `.github/workflows/*.yml`，后经 `gh auth refresh -h github.com -s workflow` 完成 device flow 授权，scopes 变为 `'gist', 'read:org', 'repo', 'workflow'`，工作流文件得以正式提交。这段限制已解除，不再是未决事项。

另外，PR #72 把 `qa.domain.coverage.minimum=0.70` 写进 `co-qa-domain/pom.xml`，因此**不依赖 CI 传参也能守住 0.70**；本机以「不加任何 `-D`」的方式验证过 `mvn verify -pl co-qa/co-qa-domain -am` 能加载 `jacoco.exec` 并通过门禁。

## 5. 结论

- #19 的**覆盖率门槛与有效性验证**：**已完成**（门槛数据见本文，CI 接线与 exec 断言见 PR #75，模块自带阈值见 PR #72）。
- #31 的**核心聚合 ≥90%**：**已达成**（`co-qa-domain` 100%，230/230，33 个测试全绿）。
- #31 的**整体 ≥70%**：**仍未达成**。基线为 42.8%（465/1086），PR #72 分支最新实测 55.6%（695/1249），两次都未达标。缺口构成很明确，不是靠多写几个单测能填的：
  - `co-bootstrap` 257 行 0%：SecurityConfig / OutboxRelay / DemoDataSeeder / GlobalExceptionHandler 等启动装配层，正确覆盖方式是集成测试（`CampusOverflowFlowIT`，需 Docker）而不是一堆 mock 单测；
  - `co-qa-application` 53.5%：命令服务仍有未覆盖的分支与装配路径；
  - 按全后端口径（把没生成报告的模块也计入分母）只会更低。
  - 基线那次覆盖率是在 `-Dmaven.test.failure.ignore=true` 下取的，含失败测试模块；第 6 节那次是**全绿**状态下取的，口径更干净，但同样**不能用于宣告整体达标**。

**结论：不造假、不靠改统计口径凑 70%。** 整体覆盖率要达标，前置条件仍是 CI runner 上跑通集成测试（#34）与剩余装配层补测，这不是单人单轮能诚实完成的。
- #34 的 `CampusOverflowFlowIT`（MySQL 8 + Redis 7 Testcontainers 全链路）代码已在 develop 上，但**本机无 Docker 未实跑**，CI 中该阶段仍 `continue-on-error`，不能算验收通过。
