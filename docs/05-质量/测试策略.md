# 测试策略

> 测试金字塔：上层少而慢，下层多而快。本项目以领域单元测试为重心。

| 层级 | 工具 | 覆盖对象 | 运行命令 | 目标 |
| --- | --- | --- | --- | --- |
| 单元测试 | JUnit 5 + Mockito | 领域聚合、值对象 | `mvn test -pl <module>` | 领域覆盖率 ≥70%，核心聚合 ≥90% |
| 应用层测试 | JUnit 5 + 假实现 | 用例编排、事件发布 | `mvn test -pl co-qa/co-qa-application` | 关键用例全覆盖 |
| 集成测试 | Testcontainers + MySQL/Redis | Controller→Service→Repository | `mvn verify` | 端到端链路通过 |
| 契约测试 | OpenAPI 校验（可选 Pact） | 前后端接口 | `npm run typecheck` + 手工核对 | S2 起每个接口有契约 |
| 端到端 | Playwright（S4 可选） | 关键用户旅程 | `npx playwright test` | 3 条主链路 |
| 架构测试 | ArchUnit | 分层与依赖 | `mvn test -pl co-bootstrap -Dtest=ArchitectureTest` | 全过 |

## 原则

1. 红-绿-重构：先看测试规格（`src/test`），再实现；
2. 不改已有测试断言；新功能必须补测试；
3. 领域层不依赖框架，测试不启 Spring 上下文；
4. 异步声誉结算用幂等消费，对账测试覆盖冻结-扣减-退还守恒；
5. 覆盖率门禁已在 S4 升级为**全模块生效**（不再是「只卡 Q&A 一个模块」），任何模块掉到 0.70 以下即红；
   `skeleton-check` 仍然必须绿——它是骨架期的遗留护栏，与覆盖率门禁并行，不互相替代。

## 覆盖率口径与门禁现状

门禁只有一处定义，在 `backend/pom.xml` 的 JaCoCo 执行 `check-all-modules` 里（Issue #97 起从 CI 命令行搬回根 POM）：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 规则 | `BUNDLE` / `LINE` / `COVEREDRATIO` | 行覆盖率，不是分支覆盖率 |
| 全局阈值 | `domain.coverage.minimum = 0.75` | 只在根 POM 定义一次（2026-11-16 从 0.70 收紧） |
| 模块阈值 | 10 个有单测的模块各自覆写为 0.90~0.95 | 子模块 `<properties>` 里的同名属性会覆盖父值 |
| 生效范围 | 27 个 Maven 模块全部继承 | 父 POM 的 `<plugins>` 会被所有模块继承 |
| 失败行为 | `haltOnFailure=true` | 低于阈值直接构建失败，不会只警告 |
| 逃生舱 | `jacoco.check.skip` | 只能在模块自己的 POM 覆写，且必须写清原因与解除条件；**不许用命令行 `-D` 或调低阈值绕过** |

### 分级门禁（2026-11-16 起）

全局 0.75 的锚点是最低的 `co-bootstrap`（79.4%），其余模块按实测值往下留 3~10 个点：

| 模块 | 实测行覆盖 | 门禁 |
| --- | --- | ---: |
| `co-shared-kernel` | 60/60 = 100% | 0.95 |
| `co-identity-application` | 155/155 = 100% | 0.95 |
| `co-qa-domain` | 230/230 = 100% | 0.95 |
| `co-discovery-domain` | 88/88 = 100% | 0.95 |
| `co-reputation-domain` | 160/160 = 100% | 0.95 |
| `co-reputation-application` | 246/248 = 99.2% | 0.95 |
| `co-discovery-application` | 140/142 = 98.6% | 0.95 |
| `co-qa-application` | 317/322 = 98.4% | 0.95 |
| `co-identity-domain` | 127/136 = 93.4% | 0.90 |
| `co-bootstrap` | 204/257 = 79.4% | 0.75（继承全局） |

写成「实测 − 3~10 个点」而不是「目标值」，是为了让门禁只承担**防回退**的职责：
它不该因为业务代码正常增长而误红，也不该被当成「覆盖率越高越好」的 KPI。

没有生成 `jacoco.exec` 的模块（4 个 `api`、4 个 `interfaces`、4 个 `infrastructure`）JaCoCo 会静默跳过，
这个风险由 CI 阶段 2b 的 exec 存在性断言守住，所以「门禁绿」不等于「每个模块都真有测试」——这两件事分开验证。

**验证方式（本地实跑，两个方向都验过）**：

```bash
# 正向：分级阈值下全部通过
mvn -o -B -ntp verify -DskipITs -pl '!co-bootstrap'     # -> All coverage checks have been met.
# 反向：把阈值临时抬到 0.999，门禁必须红
mvn -o -B -ntp verify -DskipITs -pl '!co-bootstrap' -Ddomain.coverage.minimum=0.999
# -> Rule violated for bundle co-identity-domain: lines covered ratio is 0.933, but expected minimum is 0.999
```

> `-pl '!co-bootstrap'` 只是因为本机离线时 `spring-boot:repackage` 的 buildpack 插件依赖不在本地仓库，
> 与门禁本身无关；CI 上跑的是完整的 `mvn verify`。

**当前实测（本地 `mvn test` 全绿后汇总）**：有单测的 10 个模块合计 **行 1727 / 1798 = 96.1%**，
其中 5 个模块（`co-shared-kernel`、`co-identity-application`、`co-qa-domain`、`co-discovery-domain`、`co-reputation-domain`）是 100%。
复现命令：`cd backend && mvn -o test jacoco:report`，然后读各模块 `target/site/jacoco/jacoco.csv`。

> 口径提醒：网上流传的 74.3%（答辩 PDF）与 76.0%（PR #102 描述）都是更早的快照，
> 与当前代码不一致，引用时以本节数字为准。
>
> 逐模块的实测数字（含「哪些模块有类无测试」这张表）见 [`测试与覆盖率矩阵.md`](测试与覆盖率矩阵.md)。

## 集成测试为什么默认不跑

- 6 个 `*IT` 依赖 Testcontainers + Docker（MySQL / Redis 真容器），`mvn test` 阶段**不执行**，只有 `mvn verify` 才跑；
- 因此本地全量汇总「180 个测试 / 174 通过 / 0 失败 / 6 跳过」里的 6 个跳过是**集成测试**，
  不是漏测、也不是失败被吞掉；
- 这 6 个由 `.github/workflows/integration-test.yml` 在 CI 里跑（Actions 额度恢复后），
  或者本地 `mvn verify`（需要 Docker Desktop 在跑）；
- 纯领域 / 应用层测试不启 Spring 上下文，所以 `mvn test` 在无 Docker、无外网的机器上也能全绿；
  这是刻意的设计（见 ADR-001 的可测试性驱动特征），不是「测试没覆盖到才跑得快」。
