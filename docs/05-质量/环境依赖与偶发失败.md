# 环境依赖与偶发失败

> 解决的问题：CI 失败有两种——**代码真的错了**，和**环境当时不给力**。
> 这一页给出「怎么从日志判据上说清是哪一种」的清单，避免两种误判：
> 把偶发失败当成代码问题去改代码，或者把真问题当偶发、靠重跑掩盖。
>
> 每条都来自本仓库真实发生过的事，附证据。

## 一、5 类环境依赖

| # | 现象 | 根因 | 判据（日志里长什么样） | 怎么办 |
| ---: | --- | --- | --- | --- |
| 1 | `maven-clean-plugin` 解析失败 | Maven Central **429 限流** | `status code: 429, reason phrase: Too Many Requests` | 重跑失败任务，**不改代码** |
| 2 | workflow 引用了不存在的 key | `jq -e` 把关 + 空数组 | `jq: error ... Cannot index array with string` | 检查 key，不是重跑 |
| 3 | `deploy.yml` 的 job 被 skip | 缺 `DEPLOY_HOST` 等 Secret | `jobs.<id>.if` 的条件解释了跳过原因 | 属设计行为，非失败 |
| 4 | 集成测试连不上 MySQL | 本地无 Docker / 容器未起 | `Communications link failure` | 本地跳过 IT，靠 CI 的 Testcontainers |
| 5 | `git fetch` 直接崩 | 本地代理隧道证书 | `exit 0xC0000409` / `unable to get local issuer certificate` | 换 codeload 下载快照 |

## 二、怎么一眼分清「偶发」和「真错」

**偶发（重跑即可）**：

- 报错发生在**依赖下载 / 插件解析**阶段，还没轮到编译或测试；
- 报错文本里有 `429` / `Too Many Requests` / `Connection reset` / `timeout`；
- 同一个 commit 之前或之后跑过且成功。

**真错（要改代码）**：

- 报错发生在**编译、测试断言、覆盖率门禁、ArchUnit 规则**阶段；
- 报错文本里有具体文件 / 行号 / 期望值；
- 本地复现 CI（`scripts/ci-local.ps1`）同样失败。

> 判断顺序建议：**先看报错发生在哪个阶段**，再看文本里的关键字，最后才看本地能否复现。

## 三、重跑怎么做

GitHub 网页只有一个按钮，命令行要用**失败 job 所在的 run id**（不是 job id）：

```bash
curl -X POST -H "Authorization: token $TOKEN" \
  "https://api.github.com/repos/<owner>/<repo>/actions/runs/<RUN_ID>/rerun-failed-jobs"
```

run id 从 check-run 的 `details_url` 里取：

```text
.../actions/runs/44044213485/job/133905794872
                 ^^^^^^^^^^           ^^^^^^^^^^^
                 run id               job id（拿它去调会 404）
```

**最容易踩的一步**：拿 job id 去调 rerun 接口会得到 `404 Not Found`，而不是一个说清楚的错误。

## 四、一条实例（2026-11-17）

PR #153 的 `后端构建与验证` 报红。看日志发现报错发生在 `maven-clean-plugin` 解析阶段：

```text
[ERROR] Plugin org.apache.maven.plugins:maven-clean-plugin:3.4.1 or one of its dependencies could not be resolved:
        ... status code: 429, reason phrase: Too Many Requests (429)
```

**代码一行都没跑到**。处理：用 run id `44044213485` 重跑失败 job → 30 秒后
`后端构建与验证` 变 success（attempt=2），**没有改任何代码**。

如果当时误判成代码问题，就会去改一个本来没坏的文件——这类误判在发版前尤其危险。

## 五、使用建议

1. 看到红先看**报错发生在哪个阶段**，再决定是重跑还是改代码；
2. 重跑仍红 ≈ 大概率真错，去本地跑 `scripts/ci-local.ps1` 复现；
3. 真机部署相关的红，先确认是不是缺 Secret——那是设计行为，不是 bug；
4. 如果某个 job 长期 skip，**不要当成绿**，在 PR 描述里如实写明「该检查本次未执行」。
