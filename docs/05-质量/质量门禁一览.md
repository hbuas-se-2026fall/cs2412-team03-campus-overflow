## 二、架构约束（ArchUnit 11 条）

`co-bootstrap` 里的 `ArchitectureTest` 是唯一一处「代码结构」的硬约束，
违反任何一条都会让后端 job 红：

| 编号 | 规则 | 为什么有这条 |
| --- | --- | --- |
| FF-1 | `domain` 不依赖 Spring / JPA / Jackson | 领域层要能脱离框架单测 |
| FF-2 | `domain` 不依赖其它模块的 `infrastructure` | 上下文之间只能通过 `api` 交互 |
| FF-3 | `api` 模块不依赖任何实现模块 | 发布语言必须是最小面 |
| FF-4 | 每个模块行覆盖率不低于自己的阈值 | 防止覆盖被改回去 |
| FF-5 | 表名以上下文前缀开头（`qa_` / `id_` / `rep_` / `disc_`） | 多上下文共库时避免撞名 |
| FF-6 | 构造器注入，禁止字段注入 | 可测试性 |
| FF-7 | `application` 不直接依赖 `java.sql` / `jakarta.persistence` / Spring JDBC | 用例不该知道存哪 |
| FF-8 | `domain` 里不出现 `@Component` / `@Service` / `@Repository` | 聚合根不是 Bean |
| FF-9 | `@Repository` 只能出现在 `infrastructure` | 持久化实现不外溢 |
| FF-10 | `interfaces` 不依赖其它上下文的 `interfaces` | 控制器之间不互相调用 |
| FF-11 | 无循环依赖 | 27 个模块的依赖图必须是有向无环图 |

## 三、覆盖率门禁（分级，2026-11-16 起）

全局 `BUNDLE / LINE ≥ 0.75`，10 个真正跑单测的模块各自覆写为 0.90~0.95。
逐模块的实测数字见 [`测试与覆盖率矩阵.md`](测试与覆盖率矩阵.md)。

| 反例 | 结果 |
| --- | --- |
| 把阈值临时抬到 0.999 | `Rule violated for bundle co-identity-domain: lines covered ratio is 0.933` |
| 正常代码 | `All coverage checks have been met.` |

> 门禁的职责是**防回退**，不是 KPI：所有阈值都取「实测 − 3~10 个点」。

## 四、错误码一致性

`scripts/verify-error-codes.mjs` 双向核对代码与 `docs/错误码.md`：

- **文档里有、代码里没有** → 直接失败（多半是错别字或过期码）；
- **代码里有、文档里没有** → 告警（允许先写代码后补文档）。

当前 72 个错误码在两边一致。

## 五、分支保护

`develop` 要求：

1. 至少 1 名**非作者**的写权限者批准（作者不能自批）；
2. 3 个必需检查通过（`skeleton-check` / `frontend-check` / `后端构建与验证`）；
3. 分支必须与 `develop` 同步（落后时需 `Update branch`）。

第 3 条有个副作用值得记住：**必需检查绑在「本 PR 最新提交 + 当前 develop 合并点」上**，
所以每合入一个 PR，其余 PR 的检查就失效一次。批量合并时正确的顺序是
「追平 → 等自己的检查跑完 → 立刻合」，而不是并行重跑。
