## 二、架构约束（ArchUnit，11 条规则 / 9 个 FF 编号）

`co-bootstrap` 里的 `ArchitectureTest` 是唯一一处「代码结构」的硬约束，违反任何一条都会让后端 job 红。

**注意编号口径**：代码里有 **11 条 `@ArchTest` 规则，但只编了 FF-1 ~ FF-9 共 9 个号**——
`controllers_live_in_interfaces_layer` 和 `entities_live_in_infrastructure_layer` 这两条没有 FF 编号。
下表严格按 `ArchitectureTest.java` 的**实际顺序与编号**列出，不要按序号推：

| 编号 | 规则名 | 约束 | 为什么有这条 |
| --- | --- | --- | --- |
| FF-1 | `domain_layer_is_framework_free` | `domain` 不依赖 Spring / JPA / Jackson | 领域层要能脱离框架单测 |
| FF-4 | `hexagonal_layers` | 依赖只能由外向内（六边形分层方向） | 领域层不知道谁在调用它 |
| FF-2 | `contexts_communicate_only_through_published_language` | 跨上下文只能经由对方的 `api` 包或集成事件 | 上下文之间不直接耦合 |
| FF-5 | `api_packages_are_dependency_free` | `api` 包只依赖 JDK 与共享内核 | 发布语言必须最小、可被任何上下文安全引用 |
| FF-3 | `no_cycles_between_contexts` | 上下文之间不允许循环依赖 | 依赖图必须是有向无环图 |
| （无编号） | `controllers_live_in_interfaces_layer` | `@RestController` 必须住在 `..interfaces..` | 控制器不外溢 |
| （无编号） | `entities_live_in_infrastructure_layer` | `@Entity` 必须住在 `..infrastructure..` | JPA 实体是持久化模型，与领域模型分离（ADR-008） |
| FF-7 | `application_layer_does_not_touch_sql` | `application` 不碰 `java.sql` / `jakarta.persistence` / Spring JDBC | 用例编排只通过仓储端口访问数据 |
| FF-8 | `domain_is_not_managed_by_spring` | `domain` 里不出现 Spring 注解 | 领域对象由应用层显式构造 |
| FF-9 | `spring_repositories_live_in_infrastructure` | `@Repository` 只能出现在 `infrastructure` | 持久化实现不外溢 |
| FF-6 | `tables_use_context_prefix` | 表名以上下文前缀开头（`qa_` / `id_` / `rep_` / `disc_`） | 多上下文共库时避免撞名 |

> **两个容易写错的地方**（本文档初稿就写错了，已按代码更正）：
>
> 1. **覆盖率门禁不是 ArchUnit 规则**。它是根 POM 里的 `jacoco:check`，见下一节；
>    把「每个模块行覆盖率不低于阈值」写成 FF-4 是错的——**FF-4 实际是 `hexagonal_layers`**。
> 2. **代码里不存在 FF-10 / FF-11**。初稿把「`interfaces` 不依赖其它上下文的 `interfaces`」和
>    「无循环依赖」编成了 FF-10 / FF-11，实际无环规则是 **FF-3**，而前一条根本没有对应规则。
>
> 另外 `ArchitectureTest.java` 的文件头注释仍写着「FF-1 ~ FF-6」，是历史遗留（后来加到了 FF-9），
> 与本节表格不一致时**以代码为准**。


## 三、覆盖率门禁（分级，2026-11-16 起）

全局 `BUNDLE / LINE ≥ 0.75`，10 个真正跑单测的模块各自覆写为 0.90~0.95。
逐模块的实测数字见 [`测试与覆盖率矩阵.md`](测试与覆盖率矩阵.md)。

| 反例 | 结果 |
| --- | --- |
| 把阈值临时抬到 0.999 | `Rule violated for bundle co-identity-domain: lines covered ratio is 0.933` |
| 正常代码 | `All coverage checks have been met.` |

> 门禁的职责是**防回退**，不是 KPI：所有阈值都取「实测 − 3~10 个点」。

## 四、错误码一致性

`scripts/verify-error-codes.mjs` 双向核对代码与 `docs/错误码.md`：

- **文档里有、代码里没有** → 直接失败（多半是错别字或过期码）；
- **代码里有、文档里没有** → 告警（允许先写代码后补文档）。

当前 72 个错误码在两边一致。

## 五、分支保护

`develop` 要求：

1. 至少 1 名**非作者**的写权限者批准（作者不能自批）；
2. 3 个必需检查通过（`skeleton-check` / `frontend-check` / `后端构建与验证`）；
3. 分支必须与 `develop` 同步（落后时需 `Update branch`）。

第 3 条有个副作用值得记住：**必需检查绑在「本 PR 最新提交 + 当前 develop 合并点」上**，
所以每合入一个 PR，其余 PR 的检查就失效一次。批量合并时正确的顺序是
「追平 → 等自己的检查跑完 → 立刻合」，而不是并行重跑。
