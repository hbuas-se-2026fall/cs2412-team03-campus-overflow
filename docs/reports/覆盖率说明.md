## 一、门禁是怎么生效的

这一点必须先说清楚，因为它决定下面的数字可不可信。

| 项 | 现状 |
| --- | --- |
| 阈值定义位置 | `backend/pom.xml` 的 `<domain.coverage.minimum>`，**只有一处** |
| 下发方式 | 父 POM 的 `jacoco-maven-plugin` 里新增 `check-all-modules` execution，父 POM 的 `<plugins>` 被全部 27 个模块继承 |
| 绕过方式 | 仅 `jacoco.check.skip`（POM 属性），**不允许命令行 `-D` 覆盖** |
| CI 里的覆盖参数 | 已删除。此前是 `-Ddomain.coverage.minimum=0.70 -pl co-qa/co-qa-domain -am`，只守一个模块 |

换句话说：**门禁不是某个 CI 步骤里的参数，是构建本身的一部分。** 本地 `mvn verify` 和 CI 跑的是同一套规则，没有"CI 上严、本地松"的缝隙。

## 三、那个被排除的模块

`co-reputation/co-reputation-application` 在 POM 里设了 `<jacoco.check.skip>true</jacoco.check.skip>`。

**排除时的理由**（写在模块 POM 注释里）：该模块 248 行里只有 65 行被覆盖，缺口集中在声誉结算与 S3 待实现的编排分支，需要 Testcontainers 全链路才能诚实覆盖；当时选择显式登记而不是刷假数字。

**把它的分子分母加回来算：**

```
(1249 + 65) / (1643 + 248) = 1314 / 1891 = 69.5%
```

所以存在两个都真实的数字：

| 口径 | 数值 |
| --- | ---: |
| 不含 `co-reputation-application`（当前门禁口径） | **76.0%** |
| 含全部 10 个模块 | **69.5%** |

**对外表述必须带口径**。只写 76% 不提排除，被追问模块数时会站不住；只写 69.5% 又不反映门禁的实际覆盖范围。正确说法：

> 全后端覆盖率 76.0%（1249/1643 行），其中 `co-reputation-application` 因声誉结算分支依赖 S3 全链路测试而显式排除（含入为 69.5%），排除理由见该模块 POM 注释。

## 四、这个排除正在被解除

PR #100 已经为 `co-reputation-application` 补了 47 个用例（手写替身，不启 Spring、不连库），该模块行覆盖从 26.2% 提升到 **99.2%（246/248）**，并删除 POM 里的 `jacoco.check.skip`。

合并之后：

- 27 个模块**全部**纳入门禁，不再有豁免
- 全后端口径不再需要"含/不含"两套说法
- 预期整体覆盖率高于 76.0%（分子增加 181 行，分母不变）

> 本节数据来自 PR #100 的验证输出，合并前不计入上表。
