## 一、门禁是怎么生效的

这一点必须先说清楚，因为它决定下面的数字可不可信。

| 项 | 现状 |
| --- | --- |
| 阈值定义位置 | `backend/pom.xml` 的 `<domain.coverage.minimum>`，**只有一处** |
| 下发方式 | 父 POM 的 `jacoco-maven-plugin` 里新增 `check-all-modules` execution，父 POM 的 `<plugins>` 被全部 27 个模块继承 |
| 绕过方式 | 仅 `jacoco.check.skip`（POM 属性），**不允许命令行 `-D` 覆盖** |
| CI 里的覆盖参数 | 已删除。此前是 `-Ddomain.coverage.minimum=0.70 -pl co-qa/co-qa-domain -am`，只守一个模块 |
| 豁免模块 | **无**。PR #100 已解除最后一处豁免 |

换句话说：**门禁不是某个 CI 步骤里的参数，是构建本身的一部分。** 本地 `mvn verify` 和 CI 跑的是同一套规则，没有"CI 上严、本地松"的缝隙。

## 三、那个曾经被排除的模块

`co-reputation/co-reputation-application` 一度设了 `<jacoco.check.skip>true</jacoco.check.skip>`。

**当时的理由**（写在模块 POM 注释里）：该模块 248 行里只有 65 行被覆盖，缺口集中在声誉结算与 S3 待实现的编排分支，需要 Testcontainers 全链路才能诚实覆盖；选择显式登记而不是刷假数字。

**那段时期存在两个都真实的数字：**

| 口径 | 数值 |
| --- | ---: |
| 不含 `co-reputation-application` | 76.0%（1249/1643） |
| 含全部模块 | 69.5%（1314/1891） |

所以当时对外必须带口径说明，否则被追问模块数会站不住。

**现在这个歧义没有了。** PR #100 为它补了 47 个用例（手写替身，不启 Spring、不连库、不连 Redis），

- 行覆盖从 26.2% 提升到 **99.2%（246/248）**
- POM 里的 `jacoco.check.skip` 已删除
- 27 个模块全部纳入门禁，不再有豁免
- 全后端口径 **79.1%（1495/1891）**，不再需要"含/不含"两套说法

## 四、缺口在哪

| 缺口 | 位置 | 状态 |
| --- | --- | --- |
| 声誉结算分支 | `co-reputation-application` | 已补（#100） |
| 安全过滤链装配 | `co-bootstrap` 的 `SecurityConfig` | 未覆盖。正确覆盖方式是既有 IT 的 Spring 上下文，不为凑数造 `HttpSecurity` 的 mock |
| 前端 | `frontend/` | 不在 JaCoCo 口径内；由 `frontend-check`（ESLint + 类型检查 + 构建）守 |

`co-bootstrap` 剩余未覆盖的主要是安全过滤链装配。这部分刻意不造替身测试——mock 一个 `HttpSecurity` 只能证明"我 mock 了我以为的调用顺序"，证明不了真实过滤器链的行为。
