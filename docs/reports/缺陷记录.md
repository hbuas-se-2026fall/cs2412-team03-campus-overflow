## 详述

### 1. 后端镜像启动即退出

- **现象**：容器起来后立即退出，日志里找不到主类。
- **根因**：镜像构建阶段产出的 jar 文件名与 `ENTRYPOINT` 里引用的名字不一致。构建能过、镜像能推，但一运行就崩。
- **为什么难发现**：`Publish Images` 只验证"打得出来、推得上去"，不验证"起了能活"。这也是后来补 `Compose Smoke` 的直接动因。
- **修复**：统一 jar 命名，并在 compose 冒烟里加入启动健康检查。
- **验证**：`Compose Smoke (Lab8 #37)` 一次性起六个容器，健康探针通过。

### 2. 前端镜像构建不可复现

- **现象**：同一份代码在不同机器上构建，产物不一致。
- **根因**：依赖安装未锁定，缺少构建上下文约束。
- **修复**：固定依赖来源，补 `Dockerfile` 静态校验。
- **验证**：CI 中前端构建连续通过。

### 3. `nginx -t` 冒烟缺 compose DNS

- **现象**：CI 里跑 `nginx -t` 报错，本地相同配置正常。
- **根因**：`nginx -t` 在 config test 阶段会解析 `proxy_pass` 里的上游主机名，而 CI 环境不在 compose 网络里，`backend` 这个名字解析不到。
- **修复**：冒烟时注入与 compose 一致的 DNS 解析；同时把这个故障写进运维手册，避免下次重复踩。
- **验证**：冒烟步骤通过。

### 4. actuator 路径暴露边界过宽

- **现象**：原先允许的 actuator 端点范围比实际需要的大。
- **修复**：明确拒绝其余 actuator 路径，并把联调边界检查从"观察"升级为"硬断言"。
- **验证**：`Compose Smoke` 中对 actuator 暴露边界的逐项检查通过。

### 5. 标签超 5 个时静默截断

- **现象**：提交超过 5 个标签时，系统悄悄只保留前 5 个，用户以为存下了。
- **根因**：领域规则写了"标签 1–5 个"，但实现是截断而不是拒绝。
- **为什么严重**：静默截断比报错更糟——用户的数据被丢弃且毫不知情。
- **修复**：改为拒绝并返回明确的领域错误。
- **验证**：领域层单测覆盖"超 5 个应拒绝"。

### 6. 登录用户能看到教师认证入口

- **现象**：任何登录用户都能在界面上看到"教师认证"操作入口，点下去才被后端拒绝。
- **根因**：前后端契约错位——权限判断只在前端按"是否登录"做，没有按角色细分。
- **修复**：前端补角色级权限控制，课程中心页一并重做。
- **验证**：不同角色的界面差异在手工验收中确认。

### 7. 架构约束检查步骤实际未执行

- **现象**：CI 里显示"架构约束"步骤通过，但 ArchUnit 一条规则都没跑。
- **根因**：Maven 命令缺 `-am`，模块依赖未安装，surefire 也没有正确指定测试类，导致步骤空跑成功。
- **为什么严重**：**绿灯的检查没有检查任何东西**，比红灯更危险。
- **修复**：补 `-am` 与 surefire 参数，使 ArchUnit 真正执行。
- **验证**：故意引入分层违规时该步骤会红（本地验证）。

### 8. surefire 参数无效

- **现象**：Q&A 覆盖率门禁接入时发现 surefire 配置里的参数不生效。
- **修复**：修正参数写法，使测试执行范围与报告生成符合预期。
- **验证**：覆盖率报告生成了预期的模块数据。

### 9. husky 钩子从未真正触发

- **现象**：提交前格式化从未执行，但 `.husky/pre-commit` 文件在。
- **根因**：钩子脚本缺 shebang、缺工作目录切换，husky 9 的安装路径也不对。
- **修复**：修 pre-commit 脚本与 `prepare` 钩子。
- **验证**：本地提交时能看到 lint-staged 执行。

### 10. JDBC 连接字符集导致中文乱码

- **现象**：通过 JDBC 写入的中文在库里变成乱码。
- **修复**：连接串显式指定字符集。
- **验证**：注册与登录链路中文显示正常。

### 11. 两处测试长期红

- **现象**：有两个测试自骨架期就一直失败，被当成"预期红"忽略。
- **修复**：定位后确认是测试数据非法（`strangerCannotEdit` 用了不存在的用户），修正数据后转为绿。
- **验证**：`mvn test` 全绿。

### 12. 团队文档中成员 GitHub 账号错位

- **现象**：README 与团队章程里的姓名与 GitHub 账号对应关系错了两处。
- **修复**：核对后更正，并去掉成员表中的学号列。
- **验证**：文档与 GitHub 实际账号一致。

### 13. `co-reputation-application` 覆盖率豁免

- **现象**：该模块 248 行仅覆盖 65 行（26.2%），S3 编排分支未实现，达不到全局 0.70 门禁；#97 用 `jacoco.check.skip` 显式登记豁免并写明解除条件。

- **验证**：`jacoco:check (check-all-modules)` 通过，27 个模块全部纳入门禁、零豁免；已合入 `develop` @ `b6027df`。

## 流程反思

缺陷没有走 Issue 追踪，导致：

1. 缺陷总量、修复周期、复发率都无法用工具统计，只能靠 `git log --grep` 回溯；
2. 同一个缺陷的讨论散在 PR 评论里，事后复盘要翻多个地方。

如果不做成本考量，更合适的做法是：**发现缺陷即开 Issue 并打 `bug` 标签**，修复 PR 用 `Closes #N` 关联。这样缺陷记录是自动积累的，而不是事后从历史里刨。
